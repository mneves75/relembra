# CLI benchmark, 2026-10-31

The first measured numbers for the relembra CLI binary (ticket 07). The 2026-10-30 figures in the
plan and the architecture (18 ms on the hook path) came from a prototype that ran an FTS5 query,
not relembra's wake or find, and are not comparable. The raw records of the three runs are in
`cli-2026-10-31.json`.

## Verdict

- **Cold start of `relembra wake` on 20,000 memories: p50 53 to 60 ms, p95 61 to 102 ms** (three
  runs of 50, each a new process). Process start alone is 16 to 20 ms of that.
- **`relembra find`: p50 106 to 178 ms, p95 127 to 360 ms.** Find is the slow path, as the plan
  expected: it reads and retokenizes the whole readable set on every query. Warm in-process find
  (500 queries) had a p95 of 136, 152 and 277 ms, so it met the architecture's 150 ms warm gate
  in one run of three, and it is far from ticket 19's 50 ms budget. **Ticket 19 (the term
  index) is needed.**
- The machine was shared with other agents' work (video encoding, Rust builds, Codex), at a
  1-minute load of 17 to 55 on 18 cores. That inflates the tails, so read the quietest run
  (run 3) as the closest to an idle machine, and every p95 and p99 as an upper bound.

## What was measured

`bun run bench:cli` (`bun bench/cli.ts --size 20000 --runs 50`) builds a store, then times the
compiled binary one process per call, the way an agent runs it. Each command gets 5 unmeasured
warm-up runs, then 50 measured. The OS page cache is warm and nothing is purged, so "cold" means
a new process, not a cold disk. Timing is wall-clock around `spawnSync` in the bench process, so
it includes spawning.

| Name | Command | Notes |
|---|---|---|
| help | `relembra --help` | process start alone, no store |
| wake | `relembra wake` | store open, wake over the whole scope (default 9,500-byte budget) |
| hook | `relembra hook` | wake plus the SessionStart JSON |
| find | `relembra find <query>` | store open, ranked find; 10 fixed queries, cycled |
| libraryFind | `Relembra.find` in one process | 50 warm-up and 500 measured queries on one open store |

Each run checks its outputs: every command exits 0, wake starts with `<wake>`, hook carries
`"SessionStart"`, and every find returns at least one memory, so no number is for work that did
not happen.

## Artifact, dataset and machine

- **Artifact:** `bin/relembra`, built by `bun run build:cli` (`bun build --compile --aot --trim
  --no-compile-autoload-dotenv --no-compile-autoload-bunfig`) from commit 1a99a59. sha256
  `7578c882b4602c17aa5e720b9bfb5931b029699425d4e579abc2bc7f7165e337`, 38,895,474 bytes,
  darwin-arm64.
- **Dataset:** `bench/cli.ts`, seed 20261031, 20,000 memories in one scope (`bench/cli`), each 8 to 30
  words drawn from a 4,000-word invented vocabulary skewed toward its start plus 10 common English
  words, at most 280 bytes; every 1,000th memory pinned; deterministic ids and clock. Text
  sha256 `53029c60229408b4845a0de1defe91da6105241710777ffd3cf51be05a91b816`, identical in all three
  runs. The store is 19,173,376 bytes; generating it through the library took 3.6 to 5.4 s.
- **Queries:** `lavoni zominera`, `kefepe`, `zire kasuzepi`, `getuda`, `vifanoti vinizesa`,
  `puma`, `pefo pesosavo`, `tiroto`, `nukilego gebafa`, `vokabafe`.
- **Machine:** Apple M5 Pro (`sysctl -n machdep.cpu.brand_string`), 64 GiB RAM (`hw.memsize`
  68,719,476,736), macOS 27.2 arm64.
- **Runtimes:** Bun 1.4.4 (revision da867c60bf0bcbf9d6d36994f8ca0efa42075115), SQLite 3.54.0 (Bun's
  `node:sqlite`, embedded in the binary); Node v26.12.1 is installed but not measured here.

## Where the time goes

Not profiled: a profiler on a shared machine would add more noise than it removes. The split
between the rows is the evidence:

- Process start and runtime initialization are about 16 to 20 ms (`help`).
- wake adds about 35 to 40 ms over that: opening the store, reading every live memory in the
  scope (20,000 rows, 19 MB), parsing their revisions, ordering and rendering. Wake reads the
  whole scope because the store returns every live memory; a narrower read is a store change for
  a later ticket, not a CLI change.
- find adds about 90 to 160 ms over process start, the same as in-process find (p50 103 to 159 ms):
  ranking tokenizes and scores all 20,000 memories on every query. That is ticket 19's term index.

| Warm p95 at 20k (in-process find) | ≤ 150 ms | 136, 152, 277 ms | met in 1 of 3 runs |

| Ticket 19 warm find p95 | ≤ 50 ms | 136 to 277 ms | not met; ticket 19 owns it |
